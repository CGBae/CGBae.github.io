# 프로젝트 포트폴리오 재검토 — 2026-09-08

검토 기준: 게시 이력서 `public/bae-cheolgyu-resume.pdf`, 네 프로젝트 페이지, 프로젝트별 입력 문서와 미디어 명세, 자동주유 최종 발표 원본 영상. 페이지 검토 시작 커밋은 `5b32154`다. 사용자께서 확정한 최신 담당 역할을 과거 발표자료·분석 문서의 역할 후보보다 우선했다.

이 문서는 채용용 설명과 화면 구성에 대한 검토다. ROS2·Isaac Sim·실제 로봇을 새로 실행한 결과가 아니다. 1~5절은 최초 검토 시점의 판단과 제안이다. 자동주유 상단 영상 교체에 이어, 사용자의 후속 요청으로 네 페이지 본문 재구성을 적용했다. 적용 내용과 새 검증 결과는 6절에 기록한다.

## 1. 전체 판단

신입 로봇 소프트웨어 개발자로 어필할 소재는 충분하다. 실제 로봇·운용 UI·시뮬레이션 자료가 있고, API·좌표·상태·실행을 어떻게 연결했는지 설명할 수 있다. 네 페이지 모두 문제 정의, 기술 설명, 문제 해결, 결과와 한계를 갖추고 있다.

주요 담당 문구와 기간은 이력서에 맞는다. 다만 이력서의 짧은 역할 문장을 본문에서 충분히 증명하는 정도는 다르다. 현재 페이지는 기능과 구현을 분석한 보고서의 성격이 강하고, 본인이 해결한 문제와 선택한 이유는 상대적으로 약하다. 필요한 변화는 자료를 더 많이 늘리는 것보다 강조점과 설명 순서를 정리하는 것이다.

## 2. 공통 개선 사항

### P1 — 첫 화면에서 역할과 결과를 빠르게 파악하기 어렵다

1440×1000 데스크톱, 접힌 부록을 기준으로 측정한 값이다. 자동주유는 이번 영상 교체 후의 레이아웃이다. 글꼴·창 크기에 따라 값은 달라진다.

| 프로젝트 | 대표 영상 시작 Y | 전체 문서 높이 |
| --- | ---: | ---: |
| TurtleBot4 | 889px | 10,594px |
| Automatic Fueling Robot | 1,008px | 12,237px |
| DUM-E | 1,033px | 13,202px |
| PALPA | 1,033px | 14,742px |

거대한 영문 제목과 넓은 여백 때문에 결과 영상이 첫 화면 아래에 놓인다. 전체 길이가 긴 것 자체보다 핵심을 파악하려면 끝까지 많이 읽어야 하는 점이 문제다.

권장: 현재 색상과 깔끔한 스타일은 유지하면서 제목·상단 여백을 줄이고, ‘프로젝트 목적 한 문장 / 담당 2~3항목 / 시연 / 핵심 구현 바로가기’를 가까이 배치한다. 본문은 대표 문제 해결 사례 1~2개를 깊게 설명하고, 나머지 수치·도해는 펼쳐 보기로 제공한다.

### P1 — 역할 요약은 있지만 개인의 판단과 산출물이 충분히 드러나지 않는다

PALPA와 DUM-E 본문에는 여전히 ‘아래 설명은 팀 구현/팀 시스템 기준’이라는 문장이 있다. 팀 배경을 설명하는 것은 타당하지만, 이미 확정한 본인 역할과 연결된 소제목·산출물도 함께 있어야 한다.

권장: 담당 기능마다 ‘필요했던 이유 → 내가 연결/구현한 부분 → 확인한 동작’을 한 묶음으로 쓴다. 팀 시스템의 다른 부분은 연동 대상이라고 표시한다. 사용자 확인 없이 모든 함수나 팀 알고리즘 전체를 개인 단독 구현으로 바꾸지 않는다.

### P1 — 실제 구현 코드를 찾는 경로가 부족하다

네 페이지 본문에 해당 프로젝트 저장소로 연결하는 링크가 없다. PALPA의 GitHub 링크는 공식 Doosan 드라이버 참고 링크다. 상단 메뉴의 GitHub는 개인 프로필로 연결되므로 특정 구현을 확인하기에는 한 단계 이상 더 찾아야 한다. Sources에도 대부분 파일명만 적혀 있다.

권장: 각 페이지 상단에 프로젝트 저장소 링크를 두고, 대표 사례에는 관련 함수·파일 2~3개를 커밋 고정 링크로 연결한다. 코드 파일을 모두 나열하기보다 문장을 입증하는 위치를 연결한다. 실제 공개 URL과 해당 커밋의 파일 존재 여부를 확인한 후 적용한다.

### P2 — 분석용 문구와 한계 설명의 비중이 크다

‘코드와 개발 영상에서 확인’, ‘실제 대화 로그 아님’, ‘같은 빌드 근거 미확보’, ‘Windows 분석 환경의 테스트’ 등은 분석 기록으로는 유용하지만 채용용 본문 흐름을 자주 끊는다. 내부 미디어 ID인 V10/V12도 처음 읽는 사람에게 의미가 없다.

권장: 본문은 구현·판단·결과를 능동적으로 설명하고, 자료 버전·미디어 ID·세부 검증 조건은 근거 설명에 모은다. 시뮬레이션인지 실기인지, 편집 영상인지, 실제로 구현되지 않은 연결은 해당 주장 옆에 계속 명확히 표시한다. 실제 미완성 기능을 주석 정리만으로 완료 기능처럼 바꾸면 안 된다.

### P2 — 정량 결과는 새로 만들기보다 실제 기록으로 보완해야 한다

현재 자료만으로 성공률·정밀도·cycle time·속도 개선률을 추가하기 어렵다. 대신 지금 보여줄 수 있는 완료 상태, 실행 로그, 입력과 출력의 대응을 작은 증거 묶음으로 제공할 수 있다.

추가 기록을 만들 수 있다면 PALPA는 동일 경로의 변경 전후 정지·이동 기록, 자동주유는 목표·실제 EE 위치와 lock/fallback 분기, DUM-E는 입력 이미지·판정·상태 반영 예시, TurtleBot4는 탐지→목표 수신→Nav2 결과의 같은 시각대 로그가 유용하다. 이는 앞으로 확보할 자료이지 이번 검토에서 수행한 실험이 아니다.

## 3. 프로젝트별 권장 구성

### Automatic Fueling Robot

**즉시 수정한 문제:** 기존 `hero-nozzle-motion.mp4`는 최종 PPT의 13.5초 영상 중 7~13초만 발췌한 6초짜리 노즐 유지·후퇴 장면이었다. 파일 오류는 아니지만 전체 시연의 자리에 놓기에 부적절했다. 이전 미디어 명세의 ‘UI 없는 짧은 장면 우선’ 선택을 그대로 따른 것이 원인이다.

원본 프로젝트의 55.810초 최종 발표 MP4에서 00:03~00:50을 사용해 47초 시연으로 교체했다. 차량 도착, 캡 작업, 노즐 동작, 복원과 차량 이동의 원래 장면 순서를 유지했다. 1920×1080, 무음, 장면 설명 자막과 수동 재생·탐색을 제공한다. 반복 재생은 끄고 대표 영상 폭을 페이지에 맞췄다. 원본 자체가 발표용 편집 영상이므로 이를 연속 성공 시험이나 실제 주유 시간으로 해석하지 않도록 표시했다. 재생 속도는 바꾸지 않았다.

**좋은 설명:** ArUco 마커에서 작업 offset을 적용한 점, 노즐 끝과 로봇 손목 목표를 구분한 점, waypoint 명령과 RMPFlow의 역할을 분리한 점은 유지할 가치가 있다. 특히 위치 목표만으로 자세를 유지할 수 없었던 사례는 면접에서 설명하기 좋다.

**보강:** 이력서의 세 번째 담당인 Isaac Sim 환경 구성이 본문에서 거의 플랫폼 소개에 그친다. 원본 자료에 있는 주유소·차량·두 M0609의 USD 배치, articulation·camera graph·ROS2 Bridge와 인식/제어 모듈 연결을 짧은 구조 그림이나 실제 scene 화면으로 설명하는 것이 좋다. 모든 환경 설정을 나열할 필요는 없다.

**권장 순서:** 전체 시연·담당 → 환경과 모듈 연결 → 마커 목표점·좌표 처리 → waypoint·tip offset·자세 문제 해결 → 시연 결과·제한.

단순 수치 나열에 머물지 않도록 ‘왜 접근점을 나눴는지’, ‘왜 tip과 link_6를 구분해야 했는지’를 먼저 쓴다. 105°·노즐 보정값은 해당 scene의 설정이며 일반적인 정밀 삽입 성능으로 확대하지 않는다.

### PALPA

**판단:** 네 페이지 중 이력서 역할과 기술 초점의 연결이 가장 명확하다. 웹 티칭과 실제 로봇 명령 연결을 보여주며, 모션 체이닝을 자체 spline 생성이나 radius blending으로 잘못 설명하지 않는 점도 좋다.

**보강:** 티칭 탭 전체 화면 다음에 비슷한 대형 확대 화면이 이어져 읽는 길이가 늘어난다. 전체 화면과 핵심 조작 2개 정도로 줄이고, 상세 확대는 선택적으로 보게 하는 구성이 낫다. ‘관절 조작 → 저장 → 재실행’에서 내가 담당한 입력 처리·저장·명령 전달의 범위를 함께 적는다.

**대표 사례:** ‘경유점에서 감속·재출발 → radius 요청과 실제 비동기 호출 분기 확인 → 잔여 관절각을 기준으로 다음 목표 전송 → 마지막 작업점 도착 확인’ 순서가 강점이다. UI 소개보다 이 사례를 더 빨리 발견할 수 있게 한다.

**권장 순서:** 전체 시연·담당 → 웹 티칭의 조작·저장·재실행 → 웹 명령과 피드백 → 경유 이동 문제와 체이닝 구현 → 실기 동작·결과·미측정 항목.

‘자연스러운 연속 동작 구현’은 구현 목적과 방식으로 설명할 수 있다. 동일 조건의 전후 로그가 없으므로 ‘정지 횟수 N% 감소’, ‘jerk 개선’으로 바꾸지 않는다. lead 대기 timeout 반환값을 처리하지 않는 경로는 코드 개선 검토 사항으로 남겨야 한다.

### DUM-E

**판단:** 소프트웨어 전공자로서 데이터 구조·인터페이스·비동기 연동을 보여주기 좋은 프로젝트다. 다만 첫 기술 섹션이 매뉴얼 생성·구조화여서 ‘VLM 조립 검증 및 로봇 스킬 연동’이라는 역할의 핵심이 늦게 등장한다.

**보강:** ‘현재 단계 + 기준 이미지 + 관찰 이미지 → 조립 평가 → 검사 결과 전달’ 예시를 먼저 보여준다. 현재 화면은 매뉴얼 원본과 코드 동작 예시가 크고, 실제 VLM 입력과 출력이 어떻게 대응하는지는 상대적으로 약하다. 실제 저장된 평가 결과가 있으면 개인정보 등을 확인한 뒤 이를 활용한다. 코드 예시를 실행 로그로 꾸미지 않는다.

A/B라는 분석용 명칭은 각각 ‘조립 화면에서 평가’, ‘로봇 이동 후 근접 검사’처럼 독자가 이해할 수 있게 이름을 붙인다. 두 경로의 완료 상태 갱신 범위가 다르다는 사실은 유지한다.

**대표 사례:** 정적 매뉴얼과 `current_step()` 인터페이스 불일치를 live tracker 어댑터로 연결한 사례는 좋은 소재다. ‘당시 문제 → 필요한 인터페이스 → 어댑터 연결 → 오프라인에서 확인한 단계 갱신’으로 설명하고, 이를 실기 자동 완료 갱신 성공으로 확대하지 않는다.

**권장 순서:** 조립 검사·도구 전달 시연과 담당 → VLM 검사 입력/판정 → 로봇 스킬·ROS2 연결 → 문맥 전달 문제 해결 → 매뉴얼·상태 관리 배경 → 구현/미완성/검증 결과.

현재 본문이 명시한 completion 조건 전달 누락과 로봇 검사 결과의 후속 상태 전달은 중요한 미완성 경계다. 자동 진도 갱신 완료를 어필하려면 문구 수정에 앞서 원본 구현 보완과 검증이 필요하다. 매뉴얼 8단계 시연과 5단계 구현의 버전 차이도 간결하게 유지한다.

### TurtleBot4

**판단:** 팀 알고리즘과 본인의 통합·지원 역할을 구분하고 있어 역할 과장 위험은 비교적 적다. 실제 두 로봇 시연, 좌표화와 Nav2 action의 상태 흐름도 설명력 있다.

**보강:** 본인의 강점인 통합이 한 문단으로 끝나고 몰이 수식·각도·목표 갱신 규칙이 길게 이어진다. ‘추론 결과를 어떤 메시지·좌표계로 전달했는가’, ‘각 로봇의 실행 입력과 상태를 어떻게 연결하고 확인했는가’를 기술 중심에 둔다. 현재 문서의 `PoseStamped(map)`·출동/완료 topic·Nav2 결과 흐름을 활용할 수 있다.

TF/scan/DDS 로그는 좋은 통합 자료지만 오류가 보인다는 사실과 해결했다는 사실은 다르다. 실제로 수행한 설정 변경과 전후 기록이 있다면 그것을 대표 문제 해결 사례로 사용한다. 기록이 없다면 이미 해결한 장애처럼 서술하지 않는다.

**권장 순서:** 실내 시연·담당 → 추론-제어 인터페이스 통합 → 좌표와 목표 생성의 팀 배경 → Nav2 실행·상태 연결 → 통합 시험 사례 → 결과·재검증 항목.

현재 근접 대응에는 거리 회복 확인 없이 짧은 대기 후 재출발하는 제한이 본문에 남아 있다. ‘두 로봇 충돌 완전 해결’로 바꾸지 않는다. 별도 PGM 시뮬레이션 474/500도 실기기 성공률로 가져오지 않는다.

## 4. 신입 개발자로서 강조할 방향

핵심은 ‘Python·ROS2를 사용해 인식 결과, 상태와 사용자 입력을 로봇 실행에 연결하고 통합 문제를 다룰 수 있는 개발자’다. 네 프로젝트를 모두 대규모 알고리즘 단독 개발로 보이게 만들 필요가 없다.

프로젝트마다 다른 강점을 남기면 중복이 줄어든다: PALPA는 운용 UI와 모션 명령, 자동주유는 시뮬레이션 환경과 waypoint, DUM-E는 VLM 평가와 스킬 인터페이스, TurtleBot4는 ROS2 데이터 흐름과 다중 로봇 통합이다.

C/C++·Java는 이력서의 보유 언어로 기재되어 있지만 이 네 페이지의 주요 개인 구현 근거는 Python·웹·ROS2 중심이다. C++·Java까지 프로젝트 실무 경험으로 추정하게 만드는 표현은 피하고, 해당 직무에 지원할 경우 실제 별도 코드로 보완하는 것이 맞다.

## 5. 최초 검토의 적용·확인 범위

- 적용: 자동주유 대표 영상을 47초 전체 공정 시연으로 교체, 포스터·장면 설명 자막·캡션·대표 영상 폭 조정, 미디어 출처와 재생 정보 기록.
- 제안으로 정리: 네 페이지의 역할 중심 재배치, 설명 압축, 프로젝트별 코드 링크, 개인 통합 사례와 검증 자료 보강.
- 사이트 검증: Astro 검사·빌드·6개 경로 내부 링크 검사 통과. 네 페이지 1440/390/320px에서 안정된 레이아웃과 이미지 확인. 자동주유 7개 레이아웃 검사, 영상 재생·탐색·7개 자막 cue·키보드·reduced-motion·JavaScript 없는 기본 표시 확인.
- 근거 파일: `src/pages/projects/{turtlebot4,automatic-fueling,dume,palpa}.astro`, `src/data/projects.ts`, 프로젝트별 로컬 `project-facts.md`·`project-assets.md`, 게시 이력서 PDF.
- 로컬 화면·측정 결과: `.astro/project-audit-review/report.json`, `.astro/fueling-process-review/report.json`.
- 새 영상 생성 재현: `node scripts/prepare-automatic-fueling-demo.mjs [원본 MP4 경로]`. 원본·산출물 SHA-256 및 편집 범위는 같은 폴더의 `automatic-fueling-demo-media.json`에 기록.

## 6. 후속 요청에 따른 본문 재구성 적용

사용자 요청: 검토안에 따라 네 프로젝트 페이지를 수정하고 GitHub에 푸시. 기존 흰색·검정·강조색과 서체 체계를 유지하며, 담당 역할과 구현 이유를 본문의 중심으로 재배치했다.

- 공통: 상단에 목적·담당 항목·기간·장비·저장소·핵심 구현 바로가기를 모았다. 세부 수치, 반복 확대 이미지, 보조 영상과 버전 설명은 기본적으로 접힌 상세 항목에 배치했다.
- PALPA: 웹 티칭의 조작·저장·재실행과 잔여 관절각 기반 연속 이동을 두 핵심 사례로 정리했다. radius 요청과 비동기 드라이버 분기, 마지막 작업점의 도착 확인을 연결해 설명한다.
- Automatic Fueling Robot: USD·로봇 초기화·카메라 ROS2 Bridge 환경 구성을 보강하고, 마커 offset → world 목표 → 노즐 waypoint → link_6 명령의 이유를 설명했다. 상단의 47초 전체 공정 시연을 유지했다.
- DUM-E: VLM 검사 입력·판정과 로봇 스킬 연동을 먼저 배치했다. A/B 대신 조립 화면 평가·로봇 근접 검사로 설명하고, 현재 단계 어댑터를 대표 인터페이스 사례로 남겼다. 매뉴얼 생성은 팀 배경으로 축약했다.
- TurtleBot4: 추론 결과의 PoseStamped(map), 공통 목표·로봇별 토픽, Nav2 action과 미션 상태를 중심에 두었다. 팀 몰이 기하는 상세 항목으로 옮기고 관제·RViz·실기기 통합 검증을 전면에 배치했다.
- 자료 정확성: 개인 역할과 팀의 연동 대상을 구분했다. 자동주유의 고정 장면·fallback·timeout, DUM-E의 상태 전달 미완성, PALPA의 timeout 처리, TurtleBot4의 근접 재출발 제한을 유지했다. 새 성능 지표나 수행하지 않은 실기 시험을 추가하지 않았다.

### 공개 구현 링크

src/data/project-sources.json에 네 공개 저장소와 21개 구현 위치를 기록했다. 각 파일의 공개 커밋과 anchor 문자열을 HTTP 200 응답으로 확인했으며, 페이지에는 함수·파일의 커밋 고정 링크를 표시한다. 코드 링크는 해당 시스템의 구현 근거이며, 모든 줄의 개인 단독 저작을 뜻하지 않는다.
